Checks that =make test= cannot make, with why, how to run them, and what counts as a
pass. Each one is here because it needs physical hardware, a permission dialog, a
visual confirmation, or a second application to compare against.

Keep this file honest: when a claim moves from "not verified" to measured, move the
heading to DONE and record what was actually observed, not what was expected.

* Conventions

- =$REPO= is =~/workspace/spikot-win=. Commands run from there unless stated.
- A *release* build is used where timing matters; =swift build -c release=.
- =launchctl submit= is the way to run something as its own TCC responsible process
  rather than borrowing the terminal's grant. This matters for every permission check:
  run from Ghostty, a binary inherits Ghostty's Accessibility grant and reports
  =true= regardless of its own state.
- Always pair a permission test with a *control* that should fail. Without one, an
  inherited grant looks identical to a real one.

* DONE A hotkey fires its command and does not leak the keystroke
:PROPERTIES:
:ISSUE:    spikot-win-1k4.1
:VERIFIED: 2026-09-27
:END:

Why manual :: A synthetic key event does not drive Carbon hotkey dispatch. Measured:
=CGEventPost(.cghidEventTap)= for ctrl-alt-shift-F19, with the three modifiers pressed as
real key events first so the HID modifier state is genuine, produced no fire. The same
posting against a 20-line minimal receiver, =InstallEventHandler= plus
=RegisterEventHotKey= and nothing else, also produced no fire, so this is the posting
method and not =HotkeyController=. A finger on a key is the only way in.

What is already automated, so it is not part of this test: parsing and the key-code table
(=HotkeyTests.swift=, against Carbon's own =kVK_*= constants), which bindings register,
the rejection messages, duplicate detection, and that the registrations follow a config
change.

** Procedure

The config goes in a temporary file, so the real one is untouched. Note the socket path:
=sun_path= caps at 103 bytes and the default temp directory is longer than that, which the
socket layer reports rather than truncating.

#+begin_src sh
cat > /tmp/spikot-hk.json <<'JSON'
{"hotkeysEnabled": true, "logLevel": "debug",
 "hotkeys": {"ctrl-alt-shift-k": "focus right"}}
JSON
make build
SPIKOT_CONFIG=/tmp/spikot-hk.json .build/debug/spikot-agent \
  --no-prompt --log-level debug --socket /tmp/spikot-hk.sock 2>&1 | tee /tmp/spikot-hk.log
#+end_src

Then, with Emacs frontmost and a buffer visible, press =ctrl-alt-shift-k= once.

Emacs is the right application to test in: an unbound =C-M-S-k= writes
="C-M-S-k is undefined"= in the echo area, so a leaked keystroke announces itself instead
of having to be spotted.

Repeat over a full-screen Firefox window, which is the case Carbon is chosen for:
=CGEventTap= would need Input Monitoring and =NSEvent.addGlobalMonitorForEvents= cannot
consume the event at all.

** Pass

- The log shows =Hotkey ctrl-alt-shift-k: focus right ok=.
- The focus moves to the next stack.
- Emacs says nothing: no ="C-M-S-k is undefined"=, no character inserted.
- The same over a full-screen Firefox window.
- No Input Monitoring entry appears in System Settings > Privacy & Security, and no
  dialog asks for one at any point.

=/opt/homebrew/bin= and its output landed in the agent log, a missing command was reported

Check it during the cutover: with the installed agent running, press =cmd-shift-g= and see

** Observed

The user ran the cutover themselves and reported, of the four default focus bindings, "the

Not separately confirmed, and left here rather than claimed: the leak check in Emacs as

- The window's =ax-frame= equals the =axFrame= printed for that stack, to the pixel on an
  application with no size quantisation. Emacs and Ghostty snap to character cells, so for them

- Nothing lands under the menu bar, which is what using =visibleFrame= rather than =frame=

|-----------------------------+---------------------+---------------------|
| =place 0 --window <Ghostty>=| 1131x1390@(10,40)   | 1132x1390@(10,40)   |
| =place 1 --window <Firefox>=| 1136x1390@(1151,40) | 1137x1390@(1151,40) |

Ghostty is one point wide of the request because it quantises to character cells; Firefox's

| first-third     | 1131x1390@(10,40)     | 1131x1390@(10,40)     |

*Against Rectangle*, indirectly but on the same window and display: before any of this,

** Why the frame writes look the way they do

Two findings, both measured here rather than taken from Rectangle on faith:

Firefox has =AXEnhancedUserInterface= set; Ghostty and Emacs do not. With it on, the position
and size writes *undo each other*: asking for =1136x1390@(1725,40)= on a window at
=3420x1390@(10,40)= gave, read back after each write, =(10,40,1136,1390)=, then
=(1725,40,3420,1390)= - the move applied and the size reverted - then =(10,40,1136,1390)=
again. The window oscillates and never reaches the target however many passes are made. It is
turned off around the writes and put back afterwards, as Rectangle does, and skipped entirely
when VoiceOver or Switch Control is running.

Before that was understood, the symptom looked like a missing second pass, so
=WindowIdentity.setFrame= gained Rectangle's size-position-size order and a read-back retry.
Both are kept: they are what Rectangle does, and the retry covers an application that lands
somewhere else for its own reasons. Neither was enough on its own.

an application and seeing a window appear. The resolution half — which of a config command, a
bundle identifier or =<Name>.app= is used — is unit-tested; the actuation is not.

** Procedure

#+begin_src sh
spikot-wm launch Firefox                 # with one window open: focuses it
spikot-wm launch fire                    # a prefix is enough
env PATH=/usr/bin:/bin spikot-wm launch Ghostty   # proves nothing shells out to rg any more
# then, with the application quit:
spikot-wm launch TextEdit                # not in the config, so this is the <Name>.app fallback
pgrep -x TextEdit                        # it is really running
spikot-wm list | grep -i textedit        # and it has a window
spikot-wm launch TextEdit                # which the second call focuses rather than relaunching
#+end_src

The bundle-identifier and command branches can be exercised without touching the real config:

#+begin_src sh
cat > /tmp/launch.json <<'JSON'
{"launch": {"Scratch": {"bundleID": "com.apple.TextEdit"},
            "Marker": {"command": ["/usr/bin/touch", "/tmp/spikot-launch-proof"]}}}
JSON
SPIKOT_CONFIG=/tmp/launch.json spikot-wm launch Scratch
SPIKOT_CONFIG=/tmp/launch.json spikot-wm launch Marker && ls /tmp/spikot-launch-proof
#+end_src

** Pass

- An application with one window is focused, not relaunched.
- An application that is not running starts, and a second call then focuses it.
- All of it works with =PATH=/usr/bin:/bin=.
- A command entry runs its argv; a bundleID entry opens that bundle.

** Observed

All of the above, with TextEdit standing in for Firefox so a browser session was not disturbed:
=launch TextEdit= from cold reported =launched TextEdit=, =pgrep -x TextEdit= gave 47027, a window
appeared within two seconds, and the next call reported =focused TextEdit 11031=. =launch Scratch=
started TextEdit through =com.apple.TextEdit=; =launch Marker= produced =/tmp/spikot-launch-proof=.
=launch Firefox=, =launch emacs= and =launch Ghostty= each focused the right window, the last with
=PATH=/usr/bin:/bin=.

*** One bug, found here rather than by reading

The first version reported =launched TextEdit= three times over while =pgrep -x TextEdit= stayed
empty. =NSWorkspace.openApplication= is asynchronous and a one-shot CLI process exits before the
request is carried out. The in-process path now waits up to ten seconds for the callback; the agent
does not wait, because blocking its main actor would freeze the socket, the menu and every hotkey.
So *the agent's launch path is not covered by the above* — everything here went through the CLI.

*** Not checked

The several-windows case, which shows the picker. See the BLOCKED entry below.

* BLOCKED The picker panel takes a keystroke
:PROPERTIES:
:ISSUE:    spikot-win-9ic.2
:END:

Why manual :: Keyboard focus. The panel's list, filter, selection, wrapping and number keys are
unit-tested as =PickerModel=; what cannot be tested is whether the panel is the key window when a
key is pressed.

Why blocked :: A shell-launched agent never became the active application, so the panel never
became key and a synthetic Escape did nothing. Everything tried, each confirmed by a log line
0.4s after showing: =NSApp.activate()= and the deprecated =activate(ignoringOtherApps:)=; under
=.accessory= and under =.regular=; from an unbundled binary and from =.build/SpikotWM.app=; with
and without =.nonactivatingPanel=; with the view explicitly made first responder. Every
combination reported =active false, key false=.

That is consistent with the macOS 14 activation rule: an application the user did not put in
front is refused activation. Nothing in this session involved a keypress - the panel was opened
by a socket request from a shell - so the refusal may be correct and the missing ingredient a
real hotkey press reaching an agent that launchd started.

What *is* confirmed: the panel draws and is on screen. =CGWindowListCopyWindowInfo= reports one
window owned by the agent at layer 3, 720x164 at (1360,342), alpha 1, centred on the 3440x1440
display, and its height follows the number of rows.

** Procedure

#+begin_src sh
make install-agent                    # the panel needs the launchd-started agent
# with two or more windows of one application open:
spikot-wm launch Firefox
#+end_src

Or bind a key to =pick= and press it, which is the case that matters:

#+begin_src json
{"hotkeys": {"alt-v": "pick"}}
#+end_src

** Pass

- The panel appears, listing =owner — title= per window, the first row highlighted.
- Typing narrows the list; Delete widens it again.
- Up and Down move the highlight and wrap at both ends.
- Return focuses the highlighted window and the panel disappears.
- 1 to 9 pick a row outright.
- Escape dismisses it and the application that was in front before is in front again.
- The agent has no Dock icon once the panel is gone, which is the activation policy going back
  to =.accessory=.

** If it still cannot take a key

The fallback is an event tap, which needs Input Monitoring - a second TCC prompt this project has
so far avoided. Worth recording the decision in =spikot-win-9ic.2= rather than adding the
permission quietly.

* TODO Retire mylauncher, in this order
:PROPERTIES:
:ISSUE:    spikot-win-9ic.3
:END:

Why manual :: The steps are edits to the live config and a deletion in =~/.local/bin=, and the
repository half must not land until the script is gone. =mylauncher= reads field 3 of
=spikot-wm list= — which is the owner *pid*, not a window id — and hands it to =focus --window=,
which feeds it to =NSRunningApplication(processIdentifier:)=. Both sides are consistently wrong,
which is why the pipeline works. Correcting either while the script is still there breaks the four
launcher keys.

** Procedure

1. Replace the four =exec mylauncher X= bindings and =alt-v= in
   =~/.config/spikot-wm/config.json= with the block in =Contrib/hotkeys.md=: =launch Firefox=,
   =launch Ghostty=, =launch Emacs=, =launch Safari=, =pick=.
2. Press each of =cmd-f=, =cmd-g=, =cmd-e=, =cmd-s= and =alt-v=, with the application running and
   with it quit.
3. =rm ~/.local/bin/mylauncher=. The copy in =Contrib/mylauncher.sh= is the only other one.
4. Only then, in the repository: flip the default =list= format from =legacy= to =tsv=, keep
   =--format legacy= reachable, and remove the pid fallback from =focus --window= together with its
   stderr deprecation notice.

** Pass

- =rm ~/.local/bin/mylauncher= breaks nothing.
- The five keys behave at least as well as they did through the script.
- =spikot-wm list= defaults to tsv with a window-id column that =focus --window= actually accepts,
  and =--format legacy= still produces the old three fields.

** Known risk at step 2

=cmd-g= used to pass =fast=, which took the first window silently. =launch= shows the picker
instead, and the picker's keyboard handling is unverified — so with several Ghostty windows that
key may put up a panel that only a click elsewhere dismisses. Check the BLOCKED picker entry first
if that matters.

* Deferred to their own issues

These are named in the plan and belong with the work that introduces them, not here:

- *Placement parity with Rectangle Pro, shortcut by shortcut* (=spikot-win-80o.8=, v0.29.0).
  Partly done and recorded in the DONE entry above: every action lands where it is computed, and
  spikot-wm's =first-third= and =center-third= reproduce the exact frames Rectangle Pro had placed
  on the same window. What remains is pressing *Rectangle's own* shortcut for each of the thirteen
  and comparing, which needs Rectangle still bound — which is why =80o.8= now blocks =1iz.1=, the
  uninstall. Use a non-quantising application for the exact-pixel assertions: Emacs and Ghostty
  snap to character cells, and Rectangle documents that an application's size restrictions take
  precedence.
- *Rectangle behaviours deliberately left unported* (=spikot-win-80o.8=). =BestEffortWindowMover=,
  which pulls a window back on screen when an application refused to shrink; a path for
  fixed-size windows; whether the thirds should walk first, centre, last on a repeat; and whether a
  Rectangle-style placement should touch stack membership at all. None is a bug today, and none has
  been observed to matter on this machine.
- *Hotkey precedence during the skhd cutover* (=spikot-win-1k4.3=). *Moot, and never
  measured.* The plan was to register =alt-h= while the skhdrc line was still present and see
  which side acted, since =RegisterEventHotKey= returns =noErr= for a combination another
  process holds and nothing in the API reports the clash. The cutover happened by commenting
  out every skhdrc line at once and uninstalling skhd, so the overlap that would have shown
  precedence never existed. If the question ever matters again — another hotkey daemon, or an
  application that grabs a key — it still has to be answered by observation.
- *Menu bar item, visual confirmation* (=spikot-win-nho.1=). Most of it turned out to be
  checkable without eyes: the Accessibility API can read the agent's own status item and
  drive it. See the DONE entry above. What is still unconfirmed is only how it *looks* —
  icon legibility in a light and a dark menu bar, and spacing. The picker panel is in the same
  position: its geometry is confirmed through =CGWindowListCopyWindowInfo=, its appearance is not.

* What this file is honest about

Three things in here are recorded as *not known* rather than quietly assumed, because each was
looked into and left unresolved:

- The picker cannot be shown to take a keystroke from a shell-launched agent, after six different
  attempts. It needs the installed agent and a finger on a key.
- Hotkey precedence against another daemon's event tap was never measured, and the chance is gone:
  skhd was removed in one step rather than key by key.
- Whether skhd had Screen Recording will never be known, and no longer matters.

One more worth keeping in view: for about half an hour on 2026-09-27 the Accessibility API on this
machine stopped answering window-attribute reads for every application, from two independent
processes, while =AXIsProcessTrusted()= stayed true. It recovered with no intervention. While it
lasted, every placement failed with "has no Accessibility element" and nothing in this project was
at fault — confirmed by stashing the day's changes and rebuilding. If it happens again, that is
what it looks like.
