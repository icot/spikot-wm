Checks that =make test= cannot make, with why, how to run them, and what counts as a
pass. Each one is here because it needs physical hardware, a permission dialog, a
visual confirmation, or a second application to compare against.

Keep this file honest: when a claim moves from "not verified" to measured, move the
heading to DONE and record what was actually observed, not what was expected.

* Conventions

- =$REPO= is =~/workspace/spikot-win=. Commands run from there unless stated.
- A *release* build is used where timing matters; =swift build -c release=.
- =launchctl submit= is the way to run something as its own TCC responsible process
  rather than borrowing the terminal's grant. This matters for every permission check:
  run from Ghostty, a binary inherits Ghostty's Accessibility grant and reports
  =true= regardless of its own state.
- Always pair a permission test with a *control* that should fail. Without one, an
  inherited grant looks identical to a real one.

Why manual :: Granting Accessibility needs a click in System Settings.

** Procedure

#+begin_src sh
make bundle
open .build/SpikotWM.app          # requests Accessibility, shows the dialog
# grant it in System Settings > Privacy & Security > Accessibility
codesign -dvvv .build/SpikotWM.app 2>&1 | grep CandidateCDHash
# change a string literal in Sources/Agent/main.swift
make bundle
codesign -dvvv .build/SpikotWM.app 2>&1 | grep CandidateCDHash   # must differ
launchctl submit -l check -o /tmp/p.txt -- \
  "$PWD/.build/SpikotWM.app/Contents/MacOS/spikot-agent" --check-permissions
sleep 2; launchctl remove check; cat /tmp/p.txt
#+end_src

*** Control, which must FAIL

#+begin_src sh
launchctl submit -l ctl -o /tmp/c.txt -- "$PWD/.build/release/spikot-wm" doctor
sleep 2; launchctl remove ctl; grep accessibility /tmp/c.txt
#+end_src

** Observed

cdhash moved =sha256=88c8740c…= to =sha256=8c812c2b…= and the bundled agent still
reported =accessibility: granted=. The bundle-less control reported
=accessibility [FAIL] this process is not trusted=, which is what rules out
=launchctl submit= simply inheriting a grant.

Conclusion: ad-hoc signing plus =-r='designated => identifier "org.traf.spikot-wm"'=
gives a stable TCC identity. Without =-r= the requirement is =cdhash H"…"= and every
rebuild loses the grant.

* TODO Two windows of one application resolve to distinct ids

Why manual :: Needs a second window of one application open on the desktop. Opening one
unprompted steals focus, and a test fixture cannot produce real =AXUIElement=\s.

This is the case the whole window-identity work exists for: before it, windows were
matched by comparing bounds within 2 points, which cannot separate two windows of one
application with near-identical frames.

** Procedure

Open two Ghostty windows, ideally the same size on the same display, then:

#+begin_src sh
.build/debug/spikot-wm debug ax
#+end_src

** Pass

Two rows with =Ghostty=, *different* =windowID= values, =source= reading =private= for
both, and =agree= reading =yes=. A =geometry= in the source column means the private
symbol did not answer and the fallback ran, which is the ambiguous path.

** Partially observed

With one Ghostty window, all three windows reported =source private= and =agree yes=,
with the Accessibility frame matching the CGWindowList bounds at 0 points rather than
the 2 the old matcher allowed. So the geometry fallback is not being reached — but that
is an argument, not a measurement of the two-window case.

* BLOCKED Does skhd have Screen Recording
:PROPERTIES:
:ISSUE: spikot-win-6sd.4
:END:

Why manual :: Needs a temporary binding added to the chezmoi-managed =skhdrc=.

Titles currently come from =kAXTitle=, which needs only Accessibility. =kCGWindowName=
needs Screen Recording and is nil in every context measured so far, because TCC
attributes to the responsible process and neither Ghostty nor a bare binary has it. When
=spikot-wm= runs from a keybinding the responsible process is *skhd* instead, which may
differ.

If skhd does have it, =kCGWindowName= would populate under keybindings only, making
titles differ by launch context — worth knowing even though the AX path works either way.

** Procedure

Add to =~/.local/share/chezmoi/dot_config/skhd/skhdrc=, =chezmoi apply=, then press the key:

#+begin_example
alt - t : /Users/icoteril/workspace/spikot-win/.build/debug/spikot-wm list -f json > /tmp/skhd-titles.json 2>&1
#+end_example

#+begin_src sh
python3 -c "import json;d=json.load(open('/tmp/skhd-titles.json'));print([(w['app'],w['title']) for w in d])"
#+end_src

Then remove the binding and =chezmoi apply= again.

** Pass

Inconclusive either way is an acceptable result; the point is to record which. Titles
present tells us nothing on its own, since =kAXTitle= would supply them too. To isolate
=kCGWindowName= the probe has to read it directly rather than going through
=State.title(for:)=.

Added in spikot-win-nho.2 and checked the same way. =Settings > Log level > debug= made the

** It found two bugs

Neither was visible from the CLI, and both are the reason this feature was worth building
early:

- =spikot-win-yeh.8=: one Ghostty window listed under two stacks. =Window= is =Equatable=
  over all fields including bounds, so a window that had moved was not =　==　= to its cached
  copy; the fresh one was inserted and the stale one never removed.
- =spikot-win-yeh.9=: clicking =Layout > threeColumns= killed the agent with =Index out of

* DONE A hotkey fires its command and does not leak the keystroke
:PROPERTIES:
:ISSUE:    spikot-win-1k4.1
:VERIFIED: 2026-09-27
:END:

Why manual :: A synthetic key event does not drive Carbon hotkey dispatch. Measured:
=CGEventPost(.cghidEventTap)= for ctrl-alt-shift-F19, with the three modifiers pressed as
real key events first so the HID modifier state is genuine, produced no fire. The same
posting against a 20-line minimal receiver, =InstallEventHandler= plus
=RegisterEventHotKey= and nothing else, also produced no fire, so this is the posting
method and not =HotkeyController=. A finger on a key is the only way in.

What is already automated, so it is not part of this test: parsing and the key-code table
(=HotkeyTests.swift=, against Carbon's own =kVK_*= constants), which bindings register,
the rejection messages, duplicate detection, and that the registrations follow a config
change.

** Procedure

The config goes in a temporary file, so the real one is untouched. Note the socket path:
=sun_path= caps at 103 bytes and the default temp directory is longer than that, which the
socket layer reports rather than truncating.

#+begin_src sh
cat > /tmp/spikot-hk.json <<'JSON'
{"hotkeysEnabled": true, "logLevel": "debug",
 "hotkeys": {"ctrl-alt-shift-k": "focus right"}}
JSON
make build
SPIKOT_CONFIG=/tmp/spikot-hk.json .build/debug/spikot-agent \
  --no-prompt --log-level debug --socket /tmp/spikot-hk.sock 2>&1 | tee /tmp/spikot-hk.log
#+end_src

Then, with Emacs frontmost and a buffer visible, press =ctrl-alt-shift-k= once.

Emacs is the right application to test in: an unbound =C-M-S-k= writes
="C-M-S-k is undefined"= in the echo area, so a leaked keystroke announces itself instead
of having to be spotted.

Repeat over a full-screen Firefox window, which is the case Carbon is chosen for:
=CGEventTap= would need Input Monitoring and =NSEvent.addGlobalMonitorForEvents= cannot
consume the event at all.

** Pass

- The log shows =Hotkey ctrl-alt-shift-k: focus right ok=.
- The focus moves to the next stack.
- Emacs says nothing: no ="C-M-S-k is undefined"=, no character inserted.
- The same over a full-screen Firefox window.
- No Input Monitoring entry appears in System Settings > Privacy & Security, and no
  dialog asks for one at any point.

** Also unchecked: a GUI application started by an exec binding

Added in spikot-win-1k4.4. =exec= itself is verified over the socket, which is the same
handler a keypress reaches: =touch= created its file, =rg= resolved through
=/opt/homebrew/bin= and its output landed in the agent log, a missing command was reported
with the search path, and =false= logged =ended by exit 1=. What that does not cover is
launching a GUI application from the agent under *launchd*, which is the real use of
=cmd-shift-g= and =cmd-p=: a shell-started agent has a different session context from a
LaunchAgent, so a local check proves nothing about the installed one. No window was opened
on the user's desktop to find out.

Check it during the cutover: with the installed agent running, press =cmd-shift-g= and see
whether a Ghostty window appears. If it does not, the agent log will say why.

** Observed

The user ran the cutover themselves and reported, of the four default focus bindings, "the
keybindings work as expected", and after migrating the rest, "I have migrated all the
keybindings, which work as expected". Eleven bindings: four =focus=, three =exec= command
lines and four =exec mylauncher=. So delivery, consumption and the =exec= path all work from a
real keypress under the installed LaunchAgent, which is what could not be driven
synthetically.

Not separately confirmed, and left here rather than claimed: the leak check in Emacs as
written above, behaviour over a full-screen Firefox window, and that no Input Monitoring entry
appeared. A leaked keystroke would most likely have been noticed as a stray character, but
nobody looked for one deliberately.

* Deferred to their own issues

These are named in the plan and belong with the work that introduces them, not here:

- *Placement parity with Rectangle Pro* (=spikot-win-80o.3= through =80o.6=). Each of
  the 13 actions has to be A/B compared against Rectangle while it is still installed.
  Use a non-quantising application such as Safari or Firefox for the exact-pixel
  assertions: Emacs and Ghostty snap to character cells, so they clamp, and Rectangle
  documents that app size restrictions take precedence.
- *Hotkey precedence during the skhd cutover* (=spikot-win-1k4.3=). *Moot, and never
  measured.* The plan was to register =alt-h= while the skhdrc line was still present and see
  which side acted, since =RegisterEventHotKey= returns =noErr= for a combination another
  process holds and nothing in the API reports the clash. The cutover happened by commenting
  out every skhdrc line at once and uninstalling skhd, so the overlap that would have shown
  precedence never existed. If the question ever matters again — another hotkey daemon, or an
  application that grabs a key — it still has to be answered by observation.
- *Menu bar item, visual confirmation* (=spikot-win-nho.1=). Most of it turned out to be
  checkable without eyes: the Accessibility API can read the agent's own status item and
  drive it. See the DONE entry below. What is still unconfirmed is only how it *looks* —
  icon legibility in a light and a dark menu bar, and spacing.
